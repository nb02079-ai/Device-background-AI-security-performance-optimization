# 1. Mitigating the Impact of Malware Evolution on API Sequence-based Windows Malware Detectors (MME)

**Wei, X., Li, C., Lv, Q., Li, N., Sun, D., & Wang, Y. — IEEE TIFS, 2025** (arXiv:2408.01661)

## 1.1 문제의식

API 시퀀스 기반 탐지 모델이 **시간이 지나면서 성능이 무너진다**는 것이 출발점이다. 이를 모델 노화(model aging) 또는 개념 변화(concept drift)라 부른다.

실측 수치가 충격적이다. 2017년 데이터로 학습한 모델을 2018~2021년에 평가했더니:

| 모델 | 평균 FNR(미탐률) | 평균 F1 |
|---|---|---|
| 일반 LSTM | **22.39%** | 83.98% |
| 일반 Text-CNN | **22.70%** | 84.67% |
| 일반 Transformer | 10.26% | 93.25% |

> 학습 시점 검증셋에서는 세 모델 모두 **F1 97% 이상**을 달성했다. 그런데 4년 뒤 실제 성능은 F1 84% 수준으로 떨어졌고, 특히 **악성코드를 정상으로 오분류하는 미탐(FNR)이 22%까지 치솟았다.**

## 1.2 핵심 관찰 — Zbot 사례

저자들은 Zbot 악성코드의 진화 전후(V1 → V2)를 역공학해 비교했다. 두 버전 모두 "레지스트리 자동시작 항목에 자신을 숨기는" 동일한 악성 행위를 수행하는데:

| 관찰 | 내용 |
|---|---|
| ① API 치환 | `RegOpenKeyEx` → `RegOpenKeyTransacted`로 변경. **이름은 다르지만 동일한 행위** (탐지 회피 목적으로 트랜잭션 방식 사용) |
| ② 시스템 자원 동일 | 두 버전 모두 같은 레지스트리 키(`CurrentVersion\Run`)와 파일 경로(`<System>\lowsec`)에 접근 |
| ③ API 재사용 | `RegSetValueEx`, `RegCloseKey`는 그대로 사용. **대규모 코드 재사용으로 유사한 시퀀스 조각이 남음** |

**결론**: 악성코드는 진화해도 **의미론적으로는 유사한 행위**를 한다. 표면적 API 이름만 바뀔 뿐이다.

## 1.3 해법 (MME 프레임워크)

- **API 지식 그래프**: Windows API 공식 문서를 파싱해 76,886개 엔티티와 215,467개 관계로 그래프 구축. `RegOpenKeyEx`와 `RegOpenKeyTransacted`가 같은 action(Open), 같은 prototype(RegOpenKey), 같은 header를 공유한다는 걸 포착
- **인자(argument) 임베딩**: API 호출의 인자에서 파일경로·DLL·레지스트리키·URL·IP 5종을 추출해 계층적 해시 인코딩. 진화 전후 **접근하는 시스템 자원이 유사하다는 점**을 특징으로 활용
- **대조 학습(contrastive learning)**: 같은 family의 악성코드는 가깝게, 정상과는 멀게 임베딩

**결과**: Text-CNN 기준 FNR 13.10%p 감소(22.70%→9.60%), F1 8.47%p 향상. 유지보수 라벨링 비용도 44~52% 절감.

## 1.4 우리 연구와의 연결 ⭐

| 항목 | 시사점 |
|---|---|
| **H4(교차 데이터셋 재현)의 직접 근거** | "학습 시점 F1 97%가 4년 뒤 84%로 하락"은 우리 H1("높은 탐지 성능이 안전을 보장하지 않는다")의 시간축 버전이다. 논문 서론에 인용 가치 높음 |
| **DMBD 공식 분할 보존 결정의 정당화** | MME는 VirusTotal로 각 샘플의 출현 시점을 확보해 **월 단위 시간적 일관성**을 보장했다(TESSERACT 인용). 우리가 11.2절에서 DMBD의 2024 신종 홀드아웃을 보존하기로 한 것과 같은 원칙 |
| **관측 창 5분의 방증** | MME도 Cuckoo Sandbox에서 **샘플당 최대 실행 시간을 5분으로 설정**했다. 우리 데이터셋(DMBD 5분, CIC-MalMem 약 2.5분)의 관측 창이 학계 관행과 부합함을 보여주는 근거 |
| **레지스트리 특징의 중요성 확인** | Zbot 사례에서 악성 행위의 핵심이 레지스트리 자동시작 조작이었다. 우리 특징의 **레지스트리 이벤트율**이 포착하려는 바로 그 행위 |
| **한계 인식** | MME는 시퀀스 기반이라 우리가 쓸 수 없는 접근이다. 다만 "우리는 시퀀스를 안 쓰므로 API 치환에 의한 노화에는 상대적으로 덜 민감할 수 있다"는 가설은 세워볼 만하다 — 발생률 집계는 API 이름 변경의 영향을 받지 않기 때문. **단 이건 검증되지 않은 추측이므로 논문에 주장으로 쓰면 안 되고, 논의(Discussion)에서 가능성으로만 언급** |

**샌드박스 회피 관련 주의**: MME는 한계 절에서 **환경 인식형(environment-aware) 악성코드**를 다룬다. 샌드박스를 감지하면 악성 동작을 하지 않거나 정상 앱처럼 위장한다는 것이다. 이는 우리 1A.3절(저활동 잠복형 한계)과 같은 문제이며, 우리 데이터셋도 샌드박스에서 수집된 이상 동일한 편향을 안고 있다.

# 2. A Family of Droids — Android Malware Detection via Behavioral Modeling: Static vs Dynamic Analysis

**Onwuzurike, L., Almeida, M., Mariconti, E., Blackburn, J., Stringhini, G., & De Cristofaro, E. — PST 2018** (arXiv:1803.03448)

## 2.1 연구 설계의 미덕 — 통제된 비교

이 논문의 가치는 결과보다 **설계**에 있다. 기존 연구들이 정적 분석과 동적 분석을 각자 다른 모델·다른 특징으로 비교해왔는데, 이 논문은 **같은 모델링 기법(마르코프 체인)·같은 특징·같은 분류기(RandomForest)**로 통제해서 비교했다.

- 정적: MAMADROID (apk에서 API 호출 그래프 추출)
- 동적: AUNTIEDROID (가상 기기에서 실행하며 API 호출 추적) — Monkey(자동)와 실제 사람(크라우드소싱 5,030명) 두 방식
- 하이브리드: 두 시퀀스를 병합

**분류기로 RandomForest를 선택한 이유**: "고차원 특징 공간에서의 이진 분류에 좋은 성능을 보이기 때문" — **우리 프로토콜 4.1절 RF 채택 근거와 동일한 논리**

## 2.2 결과

| 분석 방법 | Family 모드 F1 | Package 모드 F1 |
|---|---|---|
| 정적 (MAMADROID) | 0.86 | 0.91 |
| 동적 (Monkey) | 0.86 | 0.92 |
| 동적 (사람) | 0.85 | 0.88 |
| 하이브리드 (Monkey) | 0.88 | **0.92** |

**반직관적 발견 3가지**:

1. **정적 분석이 동적 분석보다 못하지 않다.** 오히려 대등하거나 낫다. 이유는 정적 분석이 API 시퀀스를 **과대추정(overestimation)**하기 때문 — apk에서 추출 가능한 모든 행위를 포착하는 반면, 동적 분석은 실행 중 나타난 행위만 본다.

2. **사람보다 Monkey(자동 입력 생성기)가 더 나았다.** 사람은 평균 14%의 API 호출만 트리거한 반면 Monkey는 20%를 트리거했다. 같은 시간에 더 많은 이벤트를 발생시키기 때문이다.

3. **코드 커버리지가 성능을 좌우한다.** 정확히 분류된 샘플에서는 90%의 앱에서 49%의 API가 트리거된 반면, 오분류된 샘플에서는 44%에 그쳤다. 저자들의 결론: **"동적 코드 로딩 같은 회피 기법에 대한 내성을 제외하면, 코드 커버리지가 개선되지 않는 한 API 호출 기반 동적 분석 도구가 정적 분석 도구 대비 이점이 없을 수 있다."**

## 2.3 동적 코드 로딩의 충격적 수치

악성 샘플의 90%에서 **API 호출의 99.5%가 동적으로 로드**되고 있었다(정적 apk에는 없고 실행 트레이스에만 존재). 다만 정상 앱도 97%로 비슷해서, "동적 로딩 비율이 높으면 악성"이라는 판별은 불가능하다.

## 2.4 우리 연구와의 연결 ⭐

| 항목 | 시사점 |
|---|---|
| **통제된 비교 설계의 모범** | 우리 프로토콜 4.1절 모델 4종(A/B/C/D) 비교 시 참고할 설계 원칙. "같은 특징·같은 평가 기준으로 통제"가 핵심 |
| **코드 커버리지 = 우리의 관측 창 문제** | 이 논문의 "코드 커버리지" 문제는 우리 1A.3절(저활동 잠복형 탐지 불가)과 **정확히 같은 구조의 한계**다. 실행 중 드러나지 않은 행위는 특징에 반영될 수 없다 |
| **오분류 원인 분석 기법** | 상위 100개 중요 특징 중 몇 개가 각 샘플에 존재하는지 세어서, 오탐/미탐 샘플이 반대 클래스와 유사한 패턴을 보임을 입증했다. → **우리 Phase 4 특징중요도 분석에 그대로 적용 가능한 방법론** |
| **RF 선택 근거 보강** | "고차원 이진 분류에 적합" — 우리 4.1절에 인용 가능 |

**우리와 다른 점**: 이 논문은 API 호출 **시퀀스**를 마르코프 체인으로 모델링한다. 우리는 발생률 집계라 시퀀스 정보가 없다. 이 차이를 2장 관련 연구에서 명시해야 한다.

# 3. Feature-Centric Approaches to Android Malware Analysis: A Survey

**Maganur, S., Jiang, Y., Huang, J., & Zhong, F. — 2025** (arXiv:2509.10709)

## 3.1 개요

2009~2025년 논문 1,664편에서 필터링한 **68편**을 체계적으로 분석한 SLR(체계적 문헌 고찰). 정적/동적/하이브리드/그래프 네 패러다임으로 분류.

## 3.2 핵심 비교표 (논문 Table I 요약)

| 분석 유형 | 특징 | 성능 범위 | 강점 / 한계 |
|---|---|---|---|
| **정적** | 이미지 변환(DEX→이미지) | 94~99.5% | 견고, 고정밀 / 전처리 비용 |
| | API·함수호출그래프 | 89~98.22% | 의미 포착 / 그래프 구성 오버헤드 |
| | 권한(permissions) | 90~97.4% | **효율적, 확장성** / 난독화에 취약 |
| | Opcode·N-gram | 81~95.7% | 구조 패턴 / 고차원 위험 |
| **동적** | 시스템콜 추적 | 94~97.9% | 난독화 저항 / **에뮬레이터 탐지, 자원 부담** |
| | 네트워크 트래픽 | 80~94% | 코드 난독화에 강함 / 암호화 시 제약 |
| | 행위 프로파일링 | 96%+ | 포괄적 / **사용자 상호작용 필요** |
| **하이브리드** | 정적+동적 융합 | 97~99.52% | 견고성 향상 / 다중 뷰 처리 부담 |
| **그래프** | SFCG+GCN | 98.22% | 난독화에 견고 / 앵커 API 필요 |
| | 가중 이종그래프+HetGNN | 97.92% F1 | 다중 관계 융합 / 방어 없으면 취약 |

## 3.3 우리 연구에 중요한 세 가지 발견

**① 자원 제약 환경에서 동적 분석이 부적합하다는 명시적 지적**

> 동적 분석은 코드 난독화에 대한 저항성을 제공하지만 **코드 커버리지와 자원 집약성 문제**에 직면하며, 이는 자원이 제한된 IoT Android 기기에는 덜 적합하다.

→ 우리 프로토콜 7장(리소스 벤치마크)의 문제의식이 이 분야에서 **이미 인정된 제약**임을 보여준다. 논문에서 리소스 축을 왜 다루는지 정당화할 때 인용 가능.

**② 교차 데이터셋 평가에서 5~10% 성능 하락**

> 불균형은 오버샘플링을 유도하고, 오래된 데이터는 증강을 필요로 하며, **교차 평가에서는 5~10%의 성능 하락**이 나타난다.

→ **우리 H4(BCCC→DMBD 재현)의 기대치를 현실적으로 설정하는 근거**다. 완벽한 재현을 기대하면 안 되고, 5~10% 차이는 정상 범위로 봐야 한다. 프로토콜 1.1절 재현 판정 기준을 해석할 때 참고.

**③ 적대적 공격에 의한 성능 붕괴 수치**

- 난독화 변환 시 탐지율 **60% 이상 하락**
- CW 공격 하에서 정적 분석 **73.53% 하락**
- 그래프 오염 시 F1 **51.68% 하락**

→ 우리 6장(교란 민감도)에서 기대할 만한 효과 크기의 참고치. 다만 이들은 **problem-space 실행 검증을 거친 공격**이고 우리는 특징공간 교란이므로, 직접 비교는 불가하다는 점을 명심.

## 3.4 시간에 따른 성능 추세 (논문 Fig. 6 요약)

2009→2025년 평균 정확도 변화:
- 정적: 85% → 97% (난독화 한계로 정체)
- 동적: 80% → 95%
- 하이브리드: 82% → 98%
- 그래프: 78% → 98.5% (2015년 이후 가장 가파른 상승)

> **주의**: 이 수치들은 각기 다른 데이터셋·평가 설정에서 나온 것을 평균한 것이다. 저자들도 한계 절에서 "데이터셋과 평가 설정의 변동이 직접 비교를 제한한다"고 명시한다. **우리 논문에서 "선행 연구는 98% 달성" 식으로 인용하면 Arp et al.이 지적한 함정에 빠진다.**

# 4. 세 논문의 종합 시사점

## 4.1 공통 메시지

세 논문 모두 다른 각도에서 같은 말을 한다: **보고된 높은 정확도를 액면 그대로 믿으면 안 된다.**

- MME: 시간이 지나면 F1 97%가 84%로 떨어진다 (시간축)
- Family of Droids: 코드 커버리지가 낮으면 행위를 못 본다 (관측 범위축)
- Feature-Centric Survey: 교차 데이터셋에서 5~10% 떨어지고, 적대적 조건에서 60% 이상 떨어진다 (일반화·강건성축)

→ **우리 논문 H1의 문제의식이 고립된 주장이 아니라 이 분야의 축적된 인식과 일치함**을 보여주는 근거들이다.

## 4.2 프로토콜에 반영할 사항

| 항목 | 반영 내용 | 대상 절 |
|---|---|---|
| H4 기대치 현실화 | 교차 데이터셋 5~10% 성능 하락은 정상 범위 | 1.1절 재현 판정 해석 시 참고 |

## 4.3 논문에 쓰면 안 되는 것

- 세 논문의 정확도 수치를 우리 결과와 **직접 비교**하는 것 (데이터셋·평가 설정이 전부 다름)
- "우리는 시퀀스를 안 쓰므로 API 치환 기반 노화에 강하다"는 **검증되지 않은 주장** (논의에서 가능성으로만)
- Feature-Centric Survey의 연도별 평균 정확도를 **선행 연구 수준의 근거**로 쓰는 것 (저자 본인이 비교 불가를 명시)
